REUSABLE MULTI-BUILDING BIM OPERATIONS PLATFORM
ARCHITECTURE AND IMPLEMENTATION PLAN

Technology: TypeScript, Three.js, That Open Components, Fragments, web-ifc
Repository style: modular monorepo with separate frontend, backend, and database
Prepared: 2026-08-20
Document status: implementation-ready, model-agnostic plan

===============================================================================
1. PURPOSE
===============================================================================

Build a reusable web platform for viewing IFC-based buildings and connecting BIM
geometry to operational building data. The platform must support many buildings,
many IFC files, and many model versions without creating a new application or
changing source code for each building.

The existing Unity project is only a reference for useful product behavior. It is
not the architecture to reproduce. The reusable features are:

- Interactive 3D building navigation.
- BIM element hover, selection, properties, isolation, and visibility.
- Storey/spatial navigation.
- Search and selection of apartments or other managed spaces.
- Display of related operational records, such as occupants/residents.
- Clear application modes and responsive panels.
- Efficient loading of large IFC models.
- Secure separation between public model assets and private operational data.

The platform must make this workflow normal:

1. An administrator adds a building record.
2. A new IFC file is submitted to the model pipeline.
3. The pipeline validates and converts it to Fragments.
4. Building-specific configuration and unit-to-model bindings are validated.
5. A model version is published and activated.
6. The unchanged frontend and backend immediately serve the new building.

The central acceptance criterion is:

ONBOARDING A NEW BUILDING MUST REQUIRE DATA, CONFIGURATION, AND MODEL PROCESSING;
IT MUST NOT REQUIRE EDITING OR REBUILDING FEATURE CODE.

===============================================================================
2. SCOPE
===============================================================================

2.1 Core platform features
--------------------------

The first stable platform release must provide:

- Authenticated building catalog and building selection.
- One active building session at a time in the browser.
- Versioned BIM model loading from preconverted .frag assets.
- Optional context layers such as site GLB files.
- Orbit, pan, zoom, fit, reset, and touch navigation.
- BIM hover and persistent selection.
- Element identity and property inspection.
- Storey/class/type visibility and element isolation.
- Managed-space/unit search and selection.
- Geometry-to-unit and unit-to-geometry mapping.
- Related occupant/resident display subject to authorization.
- Loading, progress, cancellation, retry, empty, and error states.
- Responsive and keyboard-accessible UI.
- Model-version activation and rollback.
- Logging, audit, metrics, automated tests, and deployment controls.

2.2 Optional modules
--------------------

These should use the same extension boundaries but are not required in the first
platform release:

- Measurement and clipping planes.
- Saved viewpoints and deep links.
- Issues, annotations, and collaboration.
- First-person navigation.
- Interior-model streaming.
- Maintenance/work-order integration.
- Sensors and real-time telemetry.
- Document attachment and asset-management integrations.

2.3 Explicit non-goals
----------------------

- Do not reproduce the Unity GameObject hierarchy in Three.js.
- Do not create a custom application per IFC file or building.
- Do not hardcode floor counts, apartment counts, IFC classes, property names,
  camera coordinates, model URLs, or database row IDs in feature code.
- Do not expose That Open, Fragments, Three.js, HTTP, or SQL types to domain logic.
- Do not load and parse the full IFC in every normal browser session.
- Do not include private occupant data in static frontend files.
- Do not use object names, array position, or scene traversal order as stable IDs.

===============================================================================
3. REUSE AND MODULARITY RULES
===============================================================================

3.1 What changes per building
-----------------------------

The following are data/configuration, never application code:

- Building name, site, timezone, locale, branding, and permissions.
- Active model and historical model versions.
- IFC file, schema, units, origin, transform, and georeference.
- Default camera views and optional context layers.
- Enabled features.
- IFC import/property profile.
- Storey labels and aliases.
- Unit/space identifiers and their BIM bindings.
- Operational rows such as units, people, and occupancies.

3.2 What remains shared
-----------------------

The following are reusable platform behavior:

- Model session lifecycle.
- Camera/navigation behavior.
- Selection and highlighting.
- BIM queries and property presentation.
- Spatial tree and visibility behavior.
- Unit search and geometry mapping.
- Authorization enforcement.
- API conventions and error handling.
- Database schema and migrations.
- Model conversion, validation, publication, and rollback.
- Performance budgets, telemetry, testing, and deployment.

3.3 Stable identity rules
-------------------------

Use explicit typed identifiers:

- OrganizationId: optional ownership/tenant boundary.
- SiteId: a group of buildings.
- BuildingId: permanent business identity of a building.
- ModelId: a logical BIM model belonging to a building.
- ModelVersionId: one immutable converted version.
- ElementRef: { modelVersionId, localId, globalId? }.
- IfcGlobalId: source-stable IFC element identity when available.
- UnitId: permanent business identity of a managed unit/space.
- PersonId and OccupancyId: private operational identities.

The model-local element ID may change after reconversion. Cross-version mapping
must use IFC GlobalId or an explicit reconciliation table. UnitId must never be
derived from a display name at runtime.

3.4 Dependency direction
------------------------

Frontend:

UI components
  -> feature controllers/use cases
    -> domain interfaces (ports)
      -> HTTP and That Open adapters

Backend:

HTTP controllers
  -> application services/use cases
    -> domain rules and repository interfaces
      -> PostgreSQL/object-storage/auth adapters

Model pipeline:

pipeline commands
  -> conversion/validation services
    -> Fragments/web-ifc and storage adapters

Dependencies must point inward. Domain modules never import infrastructure.

3.5 Public module boundary
--------------------------

Every module has one public index.ts. Other modules may import only from that file.
Internal controllers, helper functions, repository implementations, and library
objects are private. Enforce this with lint/import-boundary tests.

Avoid a generic utils folder. A function belongs to the module whose vocabulary it
uses. Truly generic code must be small, independently tested, and placed in a named
package such as shared/result or shared/pagination.

===============================================================================
5. FRONTEND ARCHITECTURE
===============================================================================

5.1 Responsibility
------------------

The frontend owns presentation and user interaction. It requests data and model
assets but does not decide authorization, manipulate database rows, or convert
production IFC files.

Use TypeScript strict mode and Vite. The feature/service architecture is independent
of UI framework. Plain Web Components are sufficient; React or Vue may later
replace only presentation without changing domain services or viewer adapters.

5.2 Application state
---------------------

Use one typed store with a pure reducer:

interface AppState {
  session: { status: 'unknown' | 'anonymous' | 'authenticated' | 'expired' };
  building: { selectedId?: BuildingId; status: LoadStatus };
  model: { activeVersionId?: ModelVersionId; status: LoadStatus; progress?: number };
  mode: 'overview' | 'bim' | 'units';
  selection: { element?: ElementRef; unitId?: UnitId };
  visibility: { hiddenGroups: readonly string[]; contextVisible: boolean };
  panel: 'none' | 'properties' | 'spatialTree' | 'units' | 'occupants';
  error?: AppError;
}

The store owns durable application state. High-frequency camera matrices and raw
pointer positions stay inside ViewerService and do not cause UI-wide updates.

Required commands include SELECT_BUILDING, BUILDING_SESSION_READY,
MODEL_LOAD_STARTED/PROGRESS/COMPLETED, ENTER_MODE, SELECT_ELEMENT, SELECT_UNIT,
CLEAR_SELECTION, SET_GROUP_VISIBILITY, RESET_VIEW, and SESSION_EXPIRED.

5.4 Infrastructure adapters
---------------------------

ThatOpenViewerAdapter:

- Owns one Components registry, World, renderer, camera, FragmentsManager, and
  Highlighter integration.
- Initializes FragmentsManager once using a self-hosted worker.
- Binds loaded fragment models to the current camera.
- Updates Fragments visibility/LOD after camera-control changes.
- Converts library item maps/IDs to ElementRef.
- Disposes models, controls, canvas, listeners, worker-side state, and GPU data.

ApiClient:

- Adds authentication and correlation headers.
- Validates every response against shared runtime schemas.
- Supports AbortSignal, timeout, and stable error conversion.
- Never caches private occupant responses.

BuildingConfigAdapter:

- Converts backend configuration into frontend domain values.
- Rejects unsupported schema/runtime versions before large asset downloads.

5.5 Feature module rule
-----------------------

Each module contains public index.ts, controller/use cases, ports/types, UI,
selectors/effects, and tests. Modules communicate through the store or explicit
interfaces, never DOM lookup, global singleton, or service locator.

7.3 Relation rules
------------------

- Every unit belongs to one building.
- A building may have multiple logical models and versions.
- One approved active version per model/purpose is exposed by default.
- Unit bindings are model-version-specific because local IDs can change.
- A unit may bind to multiple model elements.
- Occupancy is time-bounded; history is not overwritten.
- People are separated from occupancy to avoid duplicated private details.
- Access is building-scoped and may be time-bounded.
- Model assets are immutable and content-addressed.

7.4 Constraints and indexes
---------------------------

Constraints include unique building code per site, unique unit code per building,
unique model version label per model, one active version rule, foreign keys, valid
occupancy date ranges, unique active binding target/version, and status checks.

Indexes include ownership foreign keys; searchable unit code/name by building;
bindings by model version + local/GlobalId; occupancy by building/unit/date; access
by user/building/date; and audit by building/time.

7.5 Migration rules
-------------------

- Forward-only ordered migrations, immutable after release.
- Expand/migrate/contract for destructive changes.
- Automated verification for every migration.
- Tested backup/restore instead of blind production down-migrations.
- Synthetic seeds only.
- Legacy imports are idempotent, transactional, dry-runnable, and reconciled.

===============================================================================
8. SHARED DOMAIN, MANIFEST, AND CONFIGURATION
===============================================================================

8.1 Shared values and schemas
-----------------------------

Shared contains branded IDs, BuildingSummary/Detail, ModelManifest, ElementRef,
ElementIdentity, ordered PropertyEntry/Group, SpatialNode, UnitSummary/Detail,
UnitBindingSet, OccupancyView, CameraPose, NamedView, FeatureFlags, PropertyProfile,
Page<T>, Result<T,E>, and stable errors.

BIM properties use ordered arrays, not object dictionaries, so duplicate keys and
source order remain representable.

Runtime validators and JSON Schema/OpenAPI cover API contracts, building config,
model manifest, conversion report, property profile, unit bindings, and publication.
Every versioned file has schemaVersion. Unsupported major versions fail before
large model downloads.

8.2 Model manifest
------------------

One immutable ModelManifest includes:

- schemaVersion, buildingId, modelId, modelVersionId, label, and hashes.
- coordinate system, units, origin transform, and georeference summary.
- default camera and named views.
- one or more fragment layers.
- optional context GLB layers.
- asset reference, hash, bytes, transform, purpose, and default visibility per layer.
- available IFC classes, property profiles, relations, storeys, and capabilities.
- unit-binding reference/version and coverage summary.
- compatible Components/Fragments/web-ifc versions.
- source fingerprint, conversion time, tools, and warnings.

No feature assumes one fixed IFC filename or scene layout.

8.3 Property profiles
---------------------

A PropertyProfile configures included IFC classes, required attributes/property
sets/relations, presentation groups/labels, searchable fields, hidden fields, and
fallback behavior. This supports different authoring conventions without branching
the frontend for a building name.

===============================================================================
9. MODEL PIPELINE
===============================================================================

9.1 Principle
-------------

Normal viewers load optimized .frag files. IFC parsing/conversion occurs in a
repeatable TypeScript pipeline using @thatopen/fragments and web-ifc. Browser IFC
import may be an admin/offline tool, not the normal public path.

9.2 Stages
----------

1. Intake: receive building/model identity, IFC, profile, context, binding rules,
   publisher; hash and stage all inputs.
2. Inspect: read schema, units, georeference, storeys, classes, GlobalIds, properties,
   relations, and warnings; always close web-ifc resources.
3. Validate: enforce support, limits, required content, coordinates, GlobalId quality,
   and profile compatibility.
4. Convert: use the pinned Fragments IfcImporter, selective content profile, and
   documented origin policy; emit content-addressed fragments.
5. Bind: match UnitId to spaces/zones/elements using declarative rules and explicit
   versioned exceptions; report mapped/unmapped/ambiguous/unmanaged.
6. Verify: load output in a verification viewer; test identity, properties, tree,
   bounds, transforms, bindings, hashes, and runtime compatibility.
7. Publish: upload immutable assets, verify remote hashes, publish manifest, register
   through backend, then activate separately with authorization.

9.3 Onboarding package
----------------------

Each building/model onboarding package contains:

- building.yaml/json
- model-source metadata
- property-profile.yaml/json
- unit-binding-rules.yaml/json
- optional unit-binding-exceptions.csv
- default/named views
- optional context-layer manifest
- validation thresholds

These are validated data contracts, not executable custom scripts. A one-building
code change requires architecture review and should become a generalized capability
or separately deployed integration adapter.

9.4 Version behavior
--------------------

Model versions/assets are immutable. New source/settings create a new version.
Activation updates an active pointer transactionally and records history. Bindings
belong to a model version. Rollback reactivates a previous verified version.

===============================================================================
10. RENDERING AND BIM ADAPTER
===============================================================================

10.1 Compatibility baseline
---------------------------

Initial tested version set:

- @thatopen/components 3.4.8
- @thatopen/components-front 3.4.4
- @thatopen/fragments 3.4.7
- three 0.184.0
- web-ifc 0.0.77
- Node at least 20.11, pinned exactly in repository and CI

Upgrade these as one tested set. Browser worker, converter, and WASM versions never
float independently.

10.2 Adapter rules
------------------

- Use Components' FragmentsManager, not a second direct FragmentsModels instance.
- Self-host matching worker/WASM files with correct MIME types.
- Hide library item maps/types behind ElementRef and target collections.
- Keep renderer/camera/model handles private.
- Query selected properties lazily; do not copy all BIM metadata into app state.
- Highlight without material cloning.
- Load context through a separate adapter/lifecycle.
- Make every model/layer handle disposable.
- Update Fragments culling/LOD after camera changes only.

The ViewerPort supports multiple/federated fragment layers, transforms, visibility,
named views, normalized picking, style/isolate/fit operations, context layers,
resize, context-loss recovery, and disposal. It contains no apartment-specific
methods; UnitBindingService resolves UnitId into generic viewer targets.

===============================================================================
11. SECURITY AND PRIVACY
===============================================================================

- Authenticate every operational-data request.
- Authorize actor + building + action on the backend.
- Apply field policy before person data serialization.
- Separate model assets from private operational data.
- Set private, no-store caching for occupant responses.
- Never put person data in static assets, URLs, logs, traces, analytics, errors,
  browser persistence, or service-worker caches.
- Audit sensitive access without response content.
- Use parameterized queries and request/response validation.
- Apply CSP, HSTS, nosniff, CORS allowlists, rate limits, and timeouts.
- Use synthetic data in development, tests, screenshots, and demos.

===============================================================================
12. COMPLETE IMPLEMENTATION PLAN
===============================================================================

Every step has outputs and acceptance criteria. Project data becomes a fixture only
after the generic capability exists.

PHASE 0 - PLATFORM REQUIREMENTS
-------------------------------

Step 0.1 - Define platform capabilities
Actions:
1. Confirm core and optional features.
2. Define browsers, devices, model-size classes, IFC schemas, and federation needs.
3. Define startup, interaction, memory, and availability targets.
4. Record non-goals and owners.
Outputs: platform scope and performance budget.
Acceptance: requirements contain no fixed model name, floor/unit count, or building-
specific camera/property assumption.

Step 0.2 - Define tenancy and privacy
Actions:
1. Define organization/site/building ownership.
2. Define roles, actions, building scope, and permitted person fields.
3. Define retention, audit, cache, backup, and incident policy.

===============================================================================
13. FUNCTION AND CODE CLARITY STANDARD
===============================================================================

- One function has one reason to change.
- Name by intent: activateModelVersion, not processModel.
- Controllers parse/validate/authorize/dispatch; no business logic.
- Services coordinate use cases and transaction boundaries.
- Repositories persist/map; they do not decide authorization.
- Adapters translate libraries/protocols to ports.
- Pure mapping/validation functions have no I/O and use table-driven tests.
- Async functions accept AbortSignal where cancellation matters.
- Resource-producing functions return explicit disposable handles.
- Avoid unclear boolean parameters; use option/value objects.
- Use Result/optional/typed errors instead of ambiguous null.
- Convert errors once at boundaries with safe context; do not log/rethrow everywhere.
- No circular feature imports or global mutable state.
- Prefer composition and small interfaces over inheritance.
- Every public function documents input, output, errors, auth, side effects,
  cancellation, and resource ownership.

Example backend flow:

GET unit occupancies
  -> route validates buildingId/unitId
  -> auth middleware resolves Actor
  -> OccupancyService requires building permission
  -> repository queries current relationships
  -> person policy filters fields
  -> response mapper validates shared schema
  -> audit records safe access metadata

Example viewer flow:

pointer select
  -> BimInteractionService asks ViewerPort to pick
  -> adapter converts library result to ElementRef
  -> service dispatches SELECT_ELEMENT
  -> BimPropertyService queries through BimQueryPort
  -> UI renders validated ordered groups

===============================================================================
14. DEFINITION OF DONE
===============================================================================

- frontend, backend, database, model-pipeline, and shared are separate, documented,
  independently tested boundaries.
- No feature code contains a building ID, model filename, floor/unit count,
  model-specific camera coordinate, or IFC hierarchy assumption.
- Two materially different buildings pass the same E2E suite.
- A third fixture building is onboarded using only data/configuration.
- Model versions are immutable, validated, activatable, and rollbackable.
- Different profiles and unit binding strategies work through contracts.
- Browser normally loads preconverted Fragments.
- Raw Three.js/That Open/Fragments types stay in frontend adapter.
- HTTP/SQL/auth/storage types stay outside domain/application logic.
- Building switch cancels stale work, clears scoped state, and disposes resources.
- BIM, spatial tree, unit search/selection, and authorized occupancy work without
  building-specific branches.
- Private data is absent from assets, caches, URLs, logs, and telemetry.
- Security, accessibility, performance, browser, DB, and lifecycle gates pass.
- New services/functions meet Section 13 clarity standard.
- Onboarding, operation, deployment, rollback, and extension are documented.

===============================================================================
15. CURRENT PROJECT AS A REFERENCE FIXTURE, NOT THE ARCHITECTURE
===============================================================================

The Unity project demonstrated useful features: 3D navigation, BIM selection and
metadata, apartment search/selection and resident relations, compact metadata,
pooled lists, and non-destructive highlighting.

It also demonstrated patterns not to copy: split mode/UI state, names/tags/hierarchy
as identity, per-element scene objects/colliders, fixed data coverage assumptions,
and private operational data in a client-readable snapshot.

Its scene and sample data are one migration/parity fixture. They do not define the
database schema, service interfaces, module names, or platform acceptance criteria.
